# Поровну — общие расходы

Учебный проект Telegram Mini App: React + TypeScript, ASP.NET Core 10, Entity Framework Core и PostgreSQL 18. Реализованы отдельные счета, участники, проверка входа Telegram и личный список счетов. Для разработки есть локальный аккаунт. Через HTTPS-туннель можно открыть приложение из Telegram и пригласить друзей в чек.

Работают добавление, редактирование, удаление с отменой последнего удаления, выбор участников и разделение блюд. Цена — от 0,01 до 1 000 000 ₽, название — до 100 символов. Суммы рассчитываются на C# в целых копейках.

**Чек, выбор участников и возможность отмены удаления сохраняются после перезапуска API и PostgreSQL.** Текущий чек предыдущего этапа перенесён в базу. Для нового проекта демонстрационный чек создаётся только один раз. Намеренно пустой чек при запуске не заполняется заново.

## Ежедневный запуск

Требуются .NET SDK 10, Node.js 22.12+ и PowerShell 7. PostgreSQL подготовлен в `.local/postgres`, данные лежат в `.local/pgdata`. Это отдельный процесс, не системная служба.

Из корня проекта, первый терминал:

```powershell
./scripts/Start-Database.ps1
./scripts/Start-Backend.ps1
```

Второй терминал:

```powershell
$env:Path = 'C:\Users\VKosolapov\AppData\Local\nvm\v24.0.0;' + $env:Path
cd frontend
npm install
npm run dev
```

Открыть http://127.0.0.1:5173 и войти локальным ключом (инструкция ниже). API требует сессию: http://127.0.0.1:5080/api/receipts. PostgreSQL принимает подключения только на `127.0.0.1:55432`, база `general_expenses`.

Остановка API и Vite — Ctrl+C в их терминалах. Остановка БД:

```powershell
./scripts/Start-Database.ps1 -Stop
```

Не удаляйте `.local/pgdata`: это ваши сохранённые данные. `.local/database.json` содержит случайный пароль локальной базы; файл игнорируется Git. Скрипт запуска передаёт строку подключения через окружение, не выводя пароль. Локальная роль `expenses` используется для разработки и тестовых баз; для публикации понадобятся отдельные роли и конфигурация.

## Архитектура и порядок чтения

Путь изменения блюда:

`AddItemForm → App → useReceipt → fetch → ReceiptController → ReceiptStore → ReceiptState → ReceiptMapping → EF Core → PostgreSQL`

1. **AddItemForm.tsx** — проверка ввода и черновик формы. Очищает поля только после успешного ответа; ошибка оставляет введённые данные.
2. **useReceipt.ts / api.ts** — загрузка и изменение подтверждённого снимка API. На время запроса формы отключаются; ожидаем ответ до 10 секунд. Клиент только форматирует суммы, не рассчитывает окончательные доли.
3. **ReceiptController.cs** — HTTP-маршруты, асинхронные вызовы сервиса и перевод ожидаемых ошибок в 400/404/409. CancellationToken приходит из запроса, чтобы отменять ненужную работу.
4. **ReceiptStore.cs** — транзакция БД, чтение, проверка версии через бизнес-логику и сохранение. Ответ об успехе возвращается только после COMMIT.
5. **ReceiptState.cs** — прежние правила чека, выделенные из хранилища: добавление, правка, удаление, выбор. Этот класс не знает SQL. Для каждой операции он восстанавливается из снимка БД.
6. **ReceiptCalculator.cs** — чистая функция расчёта. Одно блюдо делится поровну между выбравшими его участниками, остаток копеек раздаётся в стабильном порядке участников.
7. **Data/Entities.cs** — сущности, соответствующие строкам таблиц. Они отделены от DTO в `Contracts.cs`, которые описывают JSON-контракт API.
8. **Data/ExpensesDbContext.cs** — описание таблиц, ключей, связей и ограничений. DbContext отслеживает изменения сущностей и формирует SQL при SaveChangesAsync.
9. **Data/ReceiptMapping.cs** — перевод сущностей в DTO и применение нового состояния к отслеживаемым сущностям. Существующие позиции сохраняют ID, меняются только нужные строки.
10. **Data/Migrations** — первая миграция и снимок структуры EF. Миграции применяются отдельной командой, не при каждом запуске API.

## Таблицы

| Таблица | Что хранит |
|---|---|
| receipts | ID, название, дата создания, устойчивый InstanceId и номер Revision |
| participants | Участников чека и их порядок для округления |
| items | Название, цену в копейках, количество, режим деления и порядок |
| assignments | Связь позиции с выбравшим её участником |

У `items` и `participants` составной ключ `(ReceiptId, Id)`. У `assignments` ключ `(ReceiptId, ItemId, ParticipantId)`: один участник не может выбрать одну позицию дважды. Внешние ключи запрещают выбор несуществующей позиции или участника другого чека. База также ограничивает допустимую цену.

При удалении позиции сервер в одной транзакции удаляет её строку и связанные назначения, затем пересчитывает доли.

## Транзакции и конфликты

`DbContext` и `ReceiptStore` зарегистрированы как Scoped: отдельные экземпляры на запрос. DbContext не потокобезопасен и не должен быть Singleton.

При изменении PostgreSQL блокирует строку чека через `SELECT ... FOR UPDATE`. Затем код читает актуальную версию, выполняет бизнес-операцию и сохраняет изменения в одной транзакции. Это работает между разными процессами API. При ошибке весь набор изменений откатывается.

GET читает данные на уровне изоляции Repeatable Read: связанные SELECT видят согласованный снимок. Первое заполнение защищено advisory lock, поэтому два одновременных запуска не создают два демочека.

Все изменения передают `revision` и `instanceId` из последнего ответа. Revision увеличивается при сохранении; InstanceId теперь хранится в БД и **не меняется при перезапуске API**. Он меняется при создании нового чека/базы. Устаревшие запросы получают 409. Изменения другой вкладки пока нужно загрузить кнопкой «Обновить чек».

При потере ответа изменение могло уже сохраниться: обновите чек и проверьте список перед повтором. Старый номер версии защищает от повторного применения уже обработанного запроса.

## API

| Метод | Путь | Назначение |
|---|---|---|
| GET | /api/receipts/{receiptId} | Получить полный чек с рассчитанными суммами |
| POST | /api/receipts/{receiptId}/items | Добавить позицию: name, amount |
| PUT | /api/receipts/{receiptId}/items/{id} | Изменить название, цену, количество и режим |
| DELETE | /api/receipts/{receiptId}/items/{id} | Удалить позицию |
| PUT | /api/receipts/{receiptId}/items/{id}/participants/{personId} | Установить selected: true/false |
| POST | /api/receipts/{receiptId}/reset | Сбросить выбор участников |

Каждое изменение содержит также revision и instanceId. Успех возвращает полный снимок. 400 — неверный ввод, 404 — позиция отсутствует, 409 — устаревший снимок.

## Этап: «Мои счета»

Главная страница теперь показывает карточки счетов: название, дату создания, число участников и позиций, сумму. Нажмите «Создать счёт», введите название и от 1 до 12 разных имён (каждое с новой строки). Новый счёт создаётся пустым и открывается сразу. Состав участников задаётся при создании; изменение состава и названия существующего счёта пока не добавляли.

Прежний чек находится в карточке «Ужин с друзьями» с ID `demo`. Миграция `AddReceiptDetails` добавляет только Title и CreatedAt в receipts; позиции и назначения не пересоздаются. Для старого чека дата — момент применения миграции, поскольку раньше дата создания не хранилась.

- `GET /api/receipts` — краткий список счетов текущего пользователя.
- `POST /api/receipts` — создать счёт: `{ requestId: UUID, title: string, participants: string[] }`.
- `GET /api/receipts/{receiptId}` — получить конкретный счёт.
- Все операции с позициями, назначениями, сбросом и отменой имеют тот же префикс `/api/receipts/{receiptId}`. Старый адрес `/api/receipt` заменён новым.

RequestId генерируется в форме один раз. При потере ответа повтор с тем же ID возвращает ранее созданный счёт вместо дубликата. Сервер также проверяет название, количество и имена участников. Пустые, слишком длинные и повторяющиеся имена отклоняются.

### Что изучить

- `frontend/src/App.tsx`: простая навигация по hash URL; слушатель `hashchange` и его удаление при размонтировании. `#/` открывает список, `#/receipts/demo` — старый чек.
- `frontend/src/ReceiptsPage.tsx`: загрузка карточек, форма создания, состояния загрузки/ошибки/пустого списка. AbortController отменяет запрос списка при уходе со страницы.
- `frontend/src/ReceiptPage.tsx`: знакомый экран разделения, вынесенный из App. Получает receiptId через props. `key={receiptId}` создаёт независимое состояние при переходе на другой счёт.
- `frontend/src/useReceipt.ts`: запросы теперь направляются по ID выбранного счёта. ID участника больше не ограничен Аней, Борисом и Викой.
- `backend/ReceiptsController.cs`: отдельные маршруты списка и создания. В ReceiptController receiptId связывается с параметром URL.
- `backend/ReceiptStore.cs`: фильтрация всех операций по receiptId, параметризованная блокировка строки конкретного счёта, SQL-проекция карточек без загрузки всех позиций.
- `backend/Data/ReceiptMapping.cs`: ReceiptId явно передаётся и участникам, и позициям, и назначениям. Внешние ключи обеспечивают принадлежность одному счёту.

В списке видны счета, созданные пользователем, и счета, в которые он принял приглашение.

### Проверка этапа

Создайте два счёта с разными участниками. Добавьте позицию в первый, разделите её и вернитесь к списку. Откройте второй: он остаётся пустым. Удаление и сброс выбора независимы. Прямая ссылка и перезагрузка возвращают в выбранный счёт; «Назад»/«Вперёд» работают. После ухода из формы несохранённый черновик не сохраняется.

Добавлены PostgreSQL-тесты изоляции счетов, запрета чужих позиций/участников, повторного создания с одним RequestId и перехода с первоначальной схемы с сохранением старого чека. Запуск прежний: `./scripts/Test-Backend.ps1`.

## Этап: вход и личные счета

Сервер проверяет подпись Telegram.WebApp.initData по алгоритму Telegram (HMAC-SHA256), возраст данных — до 5 минут, допустимое опережение часов — 30 секунд. После входа выдаёт HttpOnly cookie на 8 часов без продления. Секрет бота остаётся только на сервере. Фронтенд не хранит токен или cookie в localStorage. При перезагрузке используется действующая сессия того же пользователя.

Миграция AddUsersAndReceiptOwners создаёт users и добавляет receipts.OwnerUserId с внешним ключом. Все прежние счета принадлежат локальному аккаунту с ID -1. Telegram ID положительные; первый посетитель не получает учебные счета. Пользователь Telegram создаёт собственные счета. Учебные счета сохраняют локального владельца.

Участник чека (имя в расчёте) и пользователь приложения (проверенный Telegram ID) — разные сущности. Сейчас владелец управляет всеми назначениями в своём чеке. Имена участников сами по себе не дают им доступ.

### Конфигурация и публикация

Для локального API скрипт читает .local/telegram.json:

~~~json
{
  "BotUsername": "porovnu_expenses_bot",
  "BotToken": "сюда вставляется токен от BotFather"
}
~~~

Папки .local/ и work/ исключены из Git. Не помещайте токен в frontend, переменные VITE_*, URL или скриншоты. .local/data-protection содержит ключи защиты серверных сессий; их также не публикуют.

На хостинге конфигурация передаётся через окружение:

- Telegram__BotToken — токен бота;
- ConnectionStrings__Expenses — подключение к PostgreSQL;
- Auth__KeysPath — постоянный приватный каталог ключей защиты cookie;
- Auth__LocalKey — необязательный локальный ключ: без него локальный вход выключен;
- Auth__AllowHttp — по умолчанию false: HTTPS и Secure cookie с SameSite=None для Telegram Web. Локальный скрипт включает HTTP и SameSite=Strict только для разработки.

Все изменяющие запросы требуют заголовок X-Requested-With: Porovnu. CORS не включён, поэтому чужая страница не может отправить такой запрос с cookie через браузер. Интерфейс и API должны иметь один origin; локально это обеспечивает Vite proxy. Ответы API имеют Cache-Control: no-store.

| Метод | Адрес | Назначение |
| --- | --- | --- |
| POST | /api/auth/telegram | Вход по { initData } с проверкой подписи |
| POST | /api/auth/local | Локальный вход по { key } |
| GET | /api/auth/me | Проверенный текущий пользователь |
| POST | /api/auth/logout | Выход из сессии |

Все маршруты счетов требуют входа. Без него ответ 401; чужой счёт возвращает 404, включая попытку повторить создание с его RequestId. Приглашённый участник после подтверждения ссылки получает доступ к чтению чека и выбору за своё место.

### Где читать код

- backend/Auth/TelegramInitData.cs — проверка подписи, времени и структуры данных.
- backend/Auth/AuthController.cs — запись пользователя в БД, вход, текущий пользователь, выход.
- backend/Auth/CurrentUser.cs — получение ID из проверенной cookie.
- backend/Program.cs — аутентификация, обязательный вход для API, защита изменяющих запросов.
- backend/ReceiptStore.cs — проверка владельца при чтении и каждой записи.
- frontend/src/AuthGate.tsx — экран входа и показ приложения только после проверки сессии.

Для первоначальной настройки скачайте Windows x64 CLI по [инструкции Microsoft](https://learn.microsoft.com/azure/developer/dev-tunnels/get-started) в .local/devtunnel.exe. Следующие команды создают туннель один раз под вашим аккаунтом GitHub и открывают для посетителей порт приложения.

~~~powershell
./.local/devtunnel.exe user login -g
./.local/devtunnel.exe create porovnu-expenses-preview --expiration 30d
./.local/devtunnel.exe port create porovnu-expenses-preview.eun1 -p 5082 --protocol http
./.local/devtunnel.exe access create porovnu-expenses-preview.eun1 --port-number 5082 --anonymous
~~~

Для @porovnu_expenses_bot уже настроена кнопка «Открыть Поровну» с адресом https://91gz75cb-5082.eun1.devtunnels.ms/. При создании нового туннеля используйте полный ID с регионом из вывода create и обновите URL кнопки на адрес порта 5082 из вывода host. При первом открытии Microsoft может показать страницу подтверждения перехода. После неё пользователь входит через Telegram. Ctrl+C останавливает процесс туннеля. Сохранённый ID можно снова запустить командой host, пока регистрация туннеля действительна.

Чтобы остановить туннель, API предпросмотра и PostgreSQL проекта из одного терминала:

~~~powershell
./scripts/Start-TelegramPreview.ps1 -Stop
~~~

Локальный режим разработки использует тот же PostgreSQL. При следующем запуске скрипт предпросмотра снова запустит базу.

### Приглашение в общий чек

Владелец выбирает имя в блоке «Пригласить участника» и нажимает «Пригласить». Telegram открывает выбор личного чата с человеком. После отмены можно снова выбрать получателя для того же приглашения. В браузере и старых клиентах Telegram доступно копирование ссылки. Место закрепляется за Telegram-аккаунтом, который первым подтвердит приглашение. Ссылка действует 48 часов. Кнопка «Заменить ссылку» отзывает прежнюю.

Новые ссылки вида https://t.me/porovnu_expenses_bot?start=invite_… открывают личный чат. Команда /start из приглашения связывает Telegram-аккаунт с участником в базе. После сохранения бот присылает название чека и кнопку «Открыть чек». При первом переходе Telegram может показать кнопку «Старт». Прежние ссылки startapp можно по-прежнему принять через поле «У меня есть приглашение».

Команды получает фоновый сервис TelegramChatBot внутри API при запуске Start-TelegramPreview.ps1. Для работы чата нужны интернет и запущенный API, для кнопки Mini App — также HTTPS-туннель. Если адрес туннеля изменится, укажите новый HTTPS-адрес в поле MiniAppUrl файла .local/telegram.json и обновите меню бота. Локальный Start-Backend.ps1 по умолчанию оставляет обработку сообщений Telegram-процессу.

Создатель счёта один раз закрепляет своё место кнопкой «Это я». Приглашённым место назначается при принятии приглашения. В обычном режиме каждый отмечает только свои блюда. Режим администратора открывает выбор за других в доступном счёте. Право задаётся числовым Telegram ID в поле AdminUserId файла .local/telegram.json.

### Порции и личные итоги

У позиции есть количество, цена за единицу и один способ распределения. В режиме «По целым порциям» кнопки «+» и «−» меняют личное количество, пока есть свободные порции. В режиме «Поровну между выбравшими» сумма всей строки делится между отметившимися. При смене режима сохраняются участники, выбравшие строку. Режим «Поровну» делит между ними всю стоимость строки. При переходе на целые порции количество распределяется максимально равномерно, остаток получают первые из выбравших по порядку мест в чеке. Порций должно хватать хотя бы по одной каждому.

Кнопка «Я закончил» фиксирует личный выбор. Пока счёт открыт, та же кнопка «Изменить чек» снимает своё подтверждение и сохраняет выбранные блюда. Если действия другого участника изменили личную долю, её нужно подтвердить снова. Для последнего подтверждения требуется распределить весь остаток. После него счёт доступен только для просмотра, включая режим администратора. Когда все места подтверждены и остаток равен нулю, сервер в той же транзакции сохраняет персональные итоги в очередь PostgreSQL. Telegram-версия отправляет их в личные чаты участников. Локальный учебный аккаунт не имеет Telegram-чата.
